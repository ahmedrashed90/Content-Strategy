# MZJ | منظومة استراتيجية المحتوى — v1.5.1

**سورس كامل للنظام المستقل**: لوحة قيادة احترافية، بنك أفكار قابل للمراجعة والاعتماد، تقويم نشر شهري، استيراد JSON متكرر، وتكليف المنفذين من سيستم التسويق بعد الاعتماد. واجهة RTL بخط **Tajawal** وألوان MZJ الأساسية **#4A211C** و**#F3E8DC**. يعمل للمستخدم المالك الحالي فقط عبر Firebase Authentication.

## تحديث v1.5.1 — إلغاء الاعتماد وإعادة المراجعة

- للفكرة المعتمدة التي **لم يُنشأ لها تاسك ولم يبدأ طلب التكليف**، يظهر زر **«إلغاء الاعتماد وإعادة للمراجعة»** في شاشة البريف.
- بعد تأكيد العملية تُعاد الفكرة إلى **بانتظار المراجعة** مع الاحتفاظ بالبريف وكامل سجل المراجعات، وتُمسح حالة اعتماد اختيار السيارات حتى يعاد الاعتماد.
- إذا كانت الفكرة مرتبطة بتاسك أو بطلب تكليف معلق، يُمنع إلغاء الاعتماد لحماية بيانات سيستم التسويق.
- يمكن إعادة اعتماد الفكرة لاحقًا من نفس الشاشة. لا يتم حذف مواعيد النشر أو تغيير بيانات الأداء السابقة.

## ما أُنجز في هذا الإصدار

1. **واجهة احترافية:** إعادة تنظيم القائمة والتنقل ولوحة القيادة، بطاقات ملخص الحالات، فصل واضح بين مراجعة الفكرة والتجهيز والتكليف، وتحسين العرض على الشاشات الصغيرة.
2. **بنك الأفكار:** بحث وفلترة بالنوع وحالة المراجعة، معاينة البريف الكامل وسجل قرارات المراجع. الحالات: `بانتظار المراجعة` → `معتمد` أو `مطلوب تعديل` أو `مرفوض`. الملاحظات إلزامية للتعديل والرفض. يتم حفظ القرار في Firestore للمستخدم المالك.
3. **اعتماد قبل التكليف:** لا يمكن تأكيد السيارات أو إرسال تكليف إلى التسويق إلا إذا كانت الفكرة `معتمد`. اختيار السيارة من الاستوك الفعلي — بدون سيارة أو سيارة/أكثر أو مقارنة سيارتين/أكثر — خطوة مستقلة عن اعتماد الفكرة.
4. **تكليف رسمي:** بعد الاعتماد واختيار السيارات، تختار نوع التاسك، **المنفذ المؤهل الموجود في سيستم التسويق**، مقاسات التسليم و**تاريخ التسليم الإلزامي**، ثم تضغط صراحة `إنشاء تاسك في سيستم التسويق`. يحتفظ النظام برقم التاسك ومعرّفات المطلوبات وتاريخ التسليم. المراجعة داخل الاستراتيجية لا تتجاوز مراجعات سيستم التسويق الأصلية.
5. **منع تكرار التكليف:** تُحفظ هوية الطلب وتفاصيله في Firestore قبل الإرسال؛ إعادة المحاولة بعد انقطاع الاتصال تستخدم نفس الطلب بدل إنشاء تاسك جديد. بعد ربط التاسك لا تُغيَّر بياناته من الاستراتيجية؛ تُدار التعديلات من سيستم التسويق نفسه.
6. **تقويم النشر والتنشيط:** عرض **شهري حقيقي** مع أسهم التنقل واختيار الشهر واليوم، بحث وفلاتر حسب المنصة والمنفذ والنوع والحالة، ملخص شهري، تفاصيل اليوم، وجدول مواعيد منظم. **تاريخ النشر منفصل عن تاريخ التسليم**. يمكن إضافة مواعيد نشر لاحقة للأفكار المعتمدة دون إعادة الاستيراد الأول.
7. **أنواع المحتوى:** في واجهات النظام واختيار أنواع المطلوب يوجد نوعان فقط: **`صورة` و`فيديو`**. فكرة الصورة يمكن أن تتطلب أكثر من صورة؛ تظهر الكمية في التفاصيل لا كنوع ثالث. بقيت البنية التاريخية للأصول الأربعة المجمعة داخليًا لضمان عدم ضياع البيانات أو كسر المراجع.
8. **استيراد دفعات JSON جديدة:** زر `استيراد أفكار JSON` موجود في بنك الأفكار والتقويم، مع تنزيل نموذج جاهز، معاينة عدد الأفكار والمكرر، ثم حفظ **الجديد فقط** في بنك الأفكار بحالة انتظار المراجعة. الاستيراد لا يمحو الأفكار السابقة أو المنشورات أو الأداء التاريخي، ولا ينشئ مهامًا تلقائيًا.
9. **الحفاظ على البيانات:** لا تغيير لمرجعي الأداء التاريخيين Facebook/Instagram/TikTok/Snapchat، ولا لنظام CRM أو مخزون العمليات؛ الربط مع التسويق قراءة بيانات الاستوك والمنفذين والكتالوج، مع **الاستثناء الوحيد: إنشاء تاسك صريح**.

## خطوات تشغيل النسخة على Vercel الحالي

**مهم:** ربط API الحالي يعمل بالفعل. **لا تحذف أو تغيّر مفاتيح Vercel التي نجح بها الاتصال**. ولا تمسح مستندات أو Collections من Firestore.

1. احتفظ بنسخة من السورس المنشور الحالي. ارفع **السورس من جذر ZIP كاملًا** إلى نفس مشروع `content-strategy` باستخدام سير عمل Git/Vercel المعتاد. لا ترفع `site/` وحده؛ لأن الملف `api/marketing-bridge.js` يجب أن يبقى Server-side.
2. إعداد المشروع الموجود: **Framework Preset: Other**، ومجلد إخراج الموقع `site` كما في `vercel.json`. احتفظ بنفس إعدادات Production والمتغيرات `MZJ_STRATEGY_READ_KEY`, `MZJ_STRATEGY_ASSIGN_KEY`, `MZJ_MARKETING_API_BASE_URL`, `MZJ_STRATEGY_FIREBASE_PROJECT_ID`, `MZJ_STRATEGY_OWNER_UID`.
3. **خطوة ضرورية قبل تجربة الاعتماد والاستيراد:** في Firebase Console افتح `Firestore Database → Rules`، وضع محتوى ملف `firestore.rules` المرفق كاملًا ثم **Publish**. هذه القواعد تسمح بمراجعة الأفكار الجديدة والقديمة وحفظ الطلب المعلّق، وتبقي وثائق الـbaselines محمية. راجع أثرها على أي مشروع Firebase آخر يشترك في نفس قاعدة البيانات قبل النشر.
4. انشر الإصدار الجديد على **Preview** أولًا، وجرّب الدخول بنفس يوزر الاستراتيجية؛ تحقق من قراءة الأفكار والتقويم ومن زر تحديث الاستوك والمنفذين. بعد التأكد انشره على **Production** في نفس المشروع.
5. افتح `مراجعة الأفكار` → فكرة → راجع البريف → `اعتماد الفكرة`، ثم `تجهيز التكليف` → اختر السيارة/السيارات → نوع المهمة والمنفذ والمقاسات و**تاريخ التسليم** → `إنشاء تاسك في سيستم التسويق`. جرّب أولًا بفكرة اختبار داخلية **فقط إذا وافقت على إنشاء تاسك حقيقي**.
6. للأفكار الجديدة: `مراجعة الأفكار` → `استيراد أفكار JSON` → تحميل/اختيار نموذج → معاينة → تأكيد. بعدها راجع كل فكرة واعتمدها. لا يلزم اختيار منفذ قبل مراجعة الفكرة؛ اختيار منفذ التسويق الحقيقي يتم أثناء إنشاء التاسك.
7. من `تقويم النشر والتنشيط` اختر الشهر وأضف تاريخ نشر لفكرة معتمدة؛ يظل ذلك **تخطيطًا فقط** ولا ينشر تلقائيًا على أي منصة.

**تنبيه:** لا تشغّل مجددًا الاستيراد الأول إذا كانت خطة الـ28 يومًا موجودة بالفعل. عملية الاستيراد الأول منفصلة عن زر **استيراد أفكار JSON** المتكرر.

## تنسيق ملف JSON الجديد

يوجد نموذج حقيقي في `data/MZJ-New-Ideas-IMPORT-TEMPLATE.json`، ويمكن تنزيل نفس النموذج من داخل النظام. كل ملف يضم من 1 إلى 80 فكرة، بصيغة:

```json
{
  "schema": "mzj-ideas-batch/v1",
  "batchId": "DEC-2026-01",
  "ideas": [
    {
      "code": "DEC26-001",
      "title": "فكرة صورة عن مقارنة مزايا السيارتين",
      "type": "image",
      "imageCount": 2,
      "platforms": ["instagram", "facebook"],
      "visualDescription": "وصف الصور وتوزيع عناصر التصميم",
      "captionsByPlatform": { "instagram": "الكابشن باللهجة السعودية" }
    },
    {
      "code": "DEC26-002",
      "title": "فكرة فيديو تفاعلي بسؤال قوي",
      "type": "video",
      "platforms": ["tiktok", "snapchat"],
      "hook": "هوك باللهجة السعودية",
      "script": "السكريبت باللهجة السعودية"
    }
  ]
}
```

`type` يقبل `image`/`video` أو `صورة`/`فيديو`. `imageCount` رقم من 1 إلى 24 للصور. الأكواد اختيارية ويولد النظام كودًا تلقائيًا عند غيابها، ويمكن ترك `executor` و`dueDate` فارغين لحين التكليف. المكرر بالعنوان أو الكود يتم تخطيه. الأصناف والمنصات وخيارات الإدخال تخضع للتحقق قبل الحفظ.

## أنواع الموافقات والتنفيذ

- **موافقة الفكرة (الاستراتيجية):** هل نص الفكرة والبريف مناسب للتنفيذ؟ `reviewStatus`.
- **اختيار السيارات المعتمدة:** حدد الموديلات الفعلية من الاستوك، منفصل عن قرار مراجعة الفكرة.
- **التكليف في التسويق:** اختيار الموظف المؤهل والتاريخ ثم إنشاء التاسك عبر API. لا يحدث تلقائيًا من زر `اعتماد الفكرة`.
- **مراجعة الملف المنتج:** تبقى داخل دورة التعديل والاعتماد الخاصة بسيستم التسويق، ولا تتغير بتغيير حالة فكرة في الاستراتيجية.

بعد إنشاء تاسك، يحتفظ النظام بمعرّف الربط. لتعديل منفذ أو تاريخ تسليم التاسك الفعلي بعد إنشائه، استخدم سيستم التسويق لضمان اتساق بيانات المنفذ والتاريخ.

## الهيكل الفني

```text
site/                    الواجهة العامة: app.js, planner.js, marketing-bridge.js, idea-import.js,
                         plan-firebase.js, styles.css, Firebase config
api/marketing-bridge.js  بروكسي محمي بهوية مالك Firebase، مفاتيح التسويق لا تخرج للمتصفح
firestore.rules          قواعد صلاحيات المالك، تشمل المراجعات والتكليفات
vercel.json              توجيه موقع site/ مع API serverless
data/                    مصادر الخطة وJSON النموذجي خارج الموقع العام
scripts/                 اختبارات محلية للبيانات والأمان وواجهة المراجعة والتكليف
qa/                      HTML ثابت للمراجعة البصرية، خارج الموقع المنشور
```
